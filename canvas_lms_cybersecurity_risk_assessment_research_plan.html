Master's Project Research Plan

Cybersecurity Risk Assessment of an Institution-Managed Canvas LMS Environment

A focused, evidence-based assessment of identity, privileged access, APIs, third-party integrations, logging, incident readiness, and continuity using NIST SP 800-30 Rev. 1 and NIST CSF 2.0.

1. Feasibility Assessment

FeasibleScope reduction recommended

The proposed project is appropriate for a master's-level project if it is framed as a risk assessment of institution-controlled Canvas configurations and integrations, rather than an attempt to assess the security of the entire Canvas SaaS platform.

Why it is feasible

  • Canvas publishes substantial security, privacy, API, OAuth, and developer-key documentation.
  • NIST SP 800-30 provides a defensible risk-assessment process.
  • NIST CSF 2.0 provides a useful structure for organizing safeguards and recommendations.
  • EDUCAUSE publishes higher-education guidance for third-party integrations and governance.
  • No penetration testing or confidential data is required.

Main feasibility problem

Public documentation cannot reveal the exact controls deployed by a particular university. Therefore, the student should not claim to measure the true residual risk of an unnamed real institution unless institutional configuration evidence is available.

Solution

Define a transparent reference institution profile. This means creating a clearly described, realistic example of the university Canvas environment that will be assessed. Because public Canvas documentation does not reveal how a specific university configures its security controls, you must state the assumptions you will use before assigning risk scores.

For example, your reference institution might be a mid-sized university that uses cloud-hosted Canvas, Microsoft Entra ID or another identity provider for SSO, MFA for employees and administrators, several Canvas administrators, an SIS integration, multiple LTI 1.3 tools, approved API developer keys, centralized logging, and an institutional incident-response process.

Transparent means that every assumption is written down clearly so the reader can distinguish between: (1) facts supported by Canvas or other published documentation, (2) assumptions about the example institution, and (3) information verified through interviews or institutional records. All likelihood, impact, and residual-risk ratings should be based on this stated profile.

Assess risks against that profile, then use interviews or institution-supplied configuration evidence only as optional validation.

2. Recommended Concrete Direction

Recommended research question:
What are the highest-priority cybersecurity risks created or influenced by institution-managed identity, privileged access, API access, third-party integrations, monitoring, and recovery practices in a cloud-hosted Canvas LMS environment, and which institution-controlled safeguards most effectively reduce those risks?

Recommended scope

Focus on six domains:

  1. Authentication and identity: SSO, MFA, account lifecycle, compromised credentials.
  2. Authorization and privileged access: administrator roles, excessive privilege, stale privileged accounts.
  3. API and developer-key security: OAuth tokens, developer-key scopes, token exposure, over-permissioned integrations.
  4. LTI and other third-party integrations: vendor access, data sharing, approval workflow, integration governance.
  5. Logging and incident readiness: detection, escalation, evidence availability, vendor/institution coordination.
  6. Availability and continuity: outage dependencies, recovery procedures, alternate teaching processes, communications.

Explicitly out of scope

  • Testing Instructure's production infrastructure.
  • Unauthorized scanning, exploitation, or vulnerability validation.
  • Reverse engineering of proprietary services.
  • Assessment of AWS infrastructure controls that are exclusively Instructure's responsibility.
  • Use of student records, credentials, or confidential institutional security data without formal authorization.

4. Research Objectives

  1. Build an asset and data-flow inventory for the reference Canvas environment.
  2. Identify realistic threat events affecting institution-controlled portions of the environment.
  3. Identify relevant vulnerabilities, weaknesses, or control gaps from public documentation and higher-education guidance.
  4. Estimate likelihood, impact, inherent risk, and residual risk using a documented scoring rubric.
  5. Map safeguards to NIST CSF 2.0 outcomes.
  6. Prioritize 12–15 risk scenarios and develop practical treatment recommendations.
  7. Evaluate whether the recommended safeguards reduce risk scores in a consistent and explainable way.

7. Step-by-Step Research Plan

1

Freeze the scope and write the assessment charter

Define the system boundary, reference institution, assumptions, exclusions, information sources, scoring model, and intended audience. State explicitly that the project evaluates risk management, not product penetration-test effectiveness.

Output: 1–2 page assessment charter.
2

Conduct the literature and standards review

Search IEEE Xplore, ACM Digital Library, Google Scholar, ProQuest, and university-library databases. Use search combinations such as:

"learning management system" AND cybersecurity risk
Canvas LMS AND security
higher education AND SaaS AND cyber risk
LTI AND security
OAuth AND LMS
API security AND higher education
third-party integration AND university cybersecurity
cloud LMS AND business continuity

Build an evidence table with columns: source, year, method, system studied, threat/control discussed, findings, limitations, and relevance to this project.

Output: literature matrix and reviewed bibliography.
3

Create the asset and data inventory

Identify assets such as user accounts, administrator accounts, course content, grades, submissions, authentication tokens, developer keys, integration secrets, audit logs, SIS data, and recovery procedures.

Classify each asset by confidentiality, integrity, and availability importance using High / Moderate / Low or a 1–5 scale.

Output: asset inventory with data classification.
4

Build the architecture and data-flow model

Model the reference environment in OWASP Threat Dragon or diagrams.net. Include:

  • Students/faculty → identity provider → Canvas.
  • Administrators → Canvas administration.
  • Canvas ↔ SIS.
  • Canvas ↔ LTI/vendor applications.
  • API clients → OAuth/developer keys → Canvas API.
  • Logs/events → institutional monitoring/SIEM where applicable.

Mark trust boundaries between the university, Instructure, end users, and third parties.

Output: architecture/data-flow diagram and trust-boundary description.
5

Develop 12–15 concrete risk scenarios

Avoid vague risks such as "hackers attack Canvas." Write each scenario as a cause–event–impact chain.

IDExample scenario
R1A compromised administrator account is used to change security-sensitive settings or access protected information because privileged access lacks sufficient authentication or review.
R2An over-scoped developer key or OAuth token allows an integration to access more Canvas data/functions than its business purpose requires.
R3A compromised third-party LTI provider exposes institutional data or creates an unauthorized path into LMS-connected workflows.
R4An inactive employee or vendor account retains access after role termination because account lifecycle processes are delayed or incomplete.
R5Security events are not investigated promptly because Canvas, IdP, integration, and institutional logs are not correlated or retained appropriately.
R6A major SaaS or integration outage disrupts teaching because the institution lacks tested continuity procedures and alternate communication methods.
Output: threat-event catalog.
6

Build the control checklist

For each scenario, document existing or expected controls and identify whether the control is primarily:

  • Instructure-managed,
  • institution-managed,
  • third-party managed, or
  • shared responsibility.

Map institution-controlled safeguards to relevant NIST CSF 2.0 outcomes. Examples include MFA, least privilege, developer-key scoping, third-party approval, access reviews, centralized logging, incident playbooks, and continuity exercises.

Output: control checklist and CSF mapping matrix.
7

Define the scoring rubric before scoring risks

Use a simple, reproducible 5×5 model.

LikelihoodDefinitionImpactDefinition
1 RareHighly unusual under defined assumptions.1 NegligibleLittle operational/data effect.
2 UnlikelyPlausible but uncommon.2 MinorLimited users/services affected.
3 PossibleCould reasonably occur.3 ModerateMeaningful disruption or data exposure.
4 LikelyExpected under common threat conditions.4 MajorSerious operational, privacy, or compliance consequences.
5 Very likelyFrequent/highly expected.5 SevereMajor institutional disruption or sensitive-data compromise.
Risk Score = Likelihood × Impact

1–4   = Low
5–9   = Moderate
10–16 = High
17–25 = Critical

Score inherent risk first. Then document applicable controls and score residual risk. Every score must have a short evidence-based rationale.

Output: scoring guide.
8

Create and populate the risk register

Required fieldsExamples
IdentificationID, asset, threat source, threat event, weakness/predisposing condition.
EvidenceCanvas documentation, NIST source, EDUCAUSE source, literature, interview code.
ScoringLikelihood, impact, inherent score, control effectiveness, residual score.
TreatmentAvoid, mitigate, transfer/share, accept.
ActionRecommended safeguard, responsible role, priority, measurement.
Output: completed prioritized risk register.
9

Optional interview validation

If human-subject approval is required by the institution, obtain it before collecting interview data. Interview 3–6 LMS administrators, IAM/security staff, or higher-education security professionals.

Use interviews to test assumptions rather than to obtain confidential security details. Example questions:

  • Which Canvas security responsibilities belong primarily to the institution?
  • Which integration risks are most difficult to govern?
  • How are privileged accounts and developer keys reviewed?
  • What evidence is typically available during an LMS-related incident?
  • Which continuity dependencies are most frequently overlooked?
Output: anonymized themes and an assumption-validation table.
10

Perform sensitivity and consistency checks

Change each High/Critical scenario's likelihood by ±1 and observe whether its priority changes substantially. If possible, have a second knowledgeable reviewer independently score a subset of risks and compare results.

This strengthens the work by showing how dependent conclusions are on subjective scoring.

Output: sensitivity table and, if applicable, reviewer-agreement results.
11

Develop the risk-treatment plan

For each High or Critical residual risk, recommend specific actions. Recommendations must be controllable by an institution and traceable to evidence.

Examples:

  • Require MFA for privileged roles.
  • Establish quarterly privileged-access reviews.
  • Require scoped developer keys and documented owners.
  • Maintain an approved LTI/integration inventory.
  • Use a formal security/privacy review before enabling new integrations.
  • Define token/key rotation and revocation procedures.
  • Correlate IdP, LMS, and integration events where feasible.
  • Create an LMS-specific incident-response playbook.
  • Exercise instructional continuity procedures annually.
Output: prioritized treatment roadmap.
12

Write the final project report

Present evidence, assumptions, scoring, and limitations transparently. The report should distinguish vendor controls from institution-controlled risks and should never imply that lack of public evidence proves a control is absent.

Output: final master's project report and appendices.

9. Analysis Strategy

The project should produce more than a checklist. Use four forms of analysis:

  1. Risk ranking: Which scenarios remain High/Critical after controls?
  2. Responsibility analysis: Which risks are institution-controlled, vendor-controlled, third-party-controlled, or shared?
  3. Control-gap analysis: Which NIST CSF 2.0 outcomes are weakly addressed in the reference environment?
  4. Sensitivity analysis: Are the top risks still top risks if likelihood assumptions change?

Optional: group risk scores by domain and create a heat map. Do not treat mathematical precision as proof; the value is consistent, transparent prioritization.

12. Quality Criteria

  • Every risk scenario is specific and includes asset, threat event, weakness, and consequence.
  • Every likelihood and impact score has a written rationale.
  • Vendor-stated controls are identified as vendor claims unless independently verified.
  • No absence-of-evidence claim is converted into a claim that a security control does not exist.
  • Institution-controlled and vendor-controlled responsibilities are clearly separated.
  • The student uses one scoring rubric consistently across all scenarios.
  • High/Critical recommendations are specific, implementable, and mapped to a recognized framework.
  • The project includes limitations and sensitivity analysis.
  • Interview participation, if used, follows institutional research/IRB requirements.

15. Final Recommendation

Proceed with the project, but use the narrower title and scope above. The strongest master's-level version is not "Is Canvas secure?" It is a structured, reproducible assessment of the risks that a university must manage when it operates Canvas as a SaaS LMS—especially identity, privileged access, APIs, LTI/third-party integrations, monitoring, incident coordination, and continuity.

This direction is manageable without unauthorized testing, provides concrete artifacts, supports defensible analysis, and produces recommendations that a university could realistically use.

Prepared as a project-planning handout. Public-source statements should be rechecked at the time the final report is written because vendor documentation and security practices can change.
