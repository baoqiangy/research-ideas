Healthcare Cybersecurity Awareness Training Accessibility Thesis Plan

A practical execution guide covering research questions, scope, environment setup, testing, data collection, analysis, and deliverables.

1. Define the Research Questions Before Testing Anything

I recommend three main questions:

RQ1: To what extent do publicly available healthcare cybersecurity awareness training materials conform to WCAG 2.1 Level AA?

RQ2: What barriers do users relying on screen readers or keyboard-only navigation encounter when completing common cybersecurity awareness training tasks?

RQ3: To what extent does the Human-Centered Healthcare Cybersecurity Awareness Framework address the accessibility failures identified, and how should its accessibility principle be extended to make it measurable?

A possible fourth question is:

RQ4: Do accessibility problems differ by training provider, content type, or assistive technology?

This keeps the thesis focused on accessibility rather than trying to prove whether disabled employees actually learn less from the material. The latter would require human-subject testing and substantially increase the scope.

2. Select and Freeze the Training-Material Dataset

You should establish the dataset before beginning testing. For example:

  • HHS 405(d) cybersecurity-awareness / Knowledge on Demand materials
  • Relevant HHS healthcare cybersecurity training or educational modules
  • CISA cybersecurity-awareness / phishing materials
  • Possibly one additional publicly available healthcare-oriented source if the dataset is otherwise too small

3. Create a Fixed Task Set

This is one of the most important methodological steps. Do not simply browse each site and report whatever problems you notice. Instead, create the same functional tasks for every applicable training module.

TaskUser goal
T1Open the training
T2Identify the training title and purpose
T3Navigate to the first lesson
T4Read lesson content
T5Access an image or infographic
T6Play/pause training video
T7Access captions/transcript
T8Move to the next section
T9Answer a quiz question
T10Submit the quiz
T11Identify whether the answer was correct
T12Navigate backward
T13Locate phishing-example information
T14Complete training without a mouse

The same applicable tasks should be attempted with every assistive-technology configuration. This converts the project from an informal website review into a repeatable experiment.

5. Add Automated Testing—but Do Not Make It the Primary Method

You can install one or two accessibility-analysis tools such as:

  • axe DevTools
  • WAVE

Automated testing is useful for detecting issues such as missing labels, contrast problems, malformed ARIA, duplicate IDs, and some structural problems.

But automated scanning should be treated as supplementary evidence. Many important failures cannot reliably be detected automatically, including confusing screen-reader announcements, inaccessible quiz feedback, incorrect focus movement, keyboard traps, illogical reading order, controls whose purpose is unclear when spoken, and interactions that technically have labels but are practically unusable.

6. Build the WCAG Evaluation Instrument

You do not necessarily need to test every WCAG criterion blindly. First determine which WCAG 2.1 Level A and AA success criteria apply to the training content.

Particularly important criteria will probably include areas involving:

  • Text alternatives
  • Captions and multimedia
  • Semantic structure
  • Meaningful sequence
  • Color and contrast
  • Keyboard accessibility
  • Focus order
  • Link purpose
  • Headings and labels
  • Visible focus
  • Error identification
  • Labels and instructions
  • Name, role, and value
  • Status messages

The evaluation sheet could look like this:

TrainingTaskWCAG SCATResultSeverityEvidence
HHS-01T92.1.1NVDAFailCriticalCannot select response
HHS-01T104.1.3JAWSFailMajorResult not announced
CISA-01T61.2.2VoiceOverPass—Captions available

Use Pass / Fail / Not Applicable / Not Tested rather than only Pass/Fail.

7. Define Severity Separately from WCAG Conformance

This would strengthen the thesis considerably. A WCAG failure does not necessarily indicate how disruptive the problem is during cybersecurity training.

  • Critical: Task cannot be completed independently.
  • Major: Task can be completed only with substantial difficulty or workaround.
  • Moderate: Information is accessible but confusing, inefficient, or incomplete.
  • Minor: Inconvenience that does not substantially interfere with task completion.

Then the results can report both the WCAG conformance failure and the practical impact on cybersecurity training.

8. Perform Each Test Systematically

For every training module, I recommend this sequence:

  1. Automated scan: Record detected accessibility issues.
  2. Keyboard-only test: Avoid the mouse and use Tab, Shift+Tab, Enter, Space, arrow keys, Escape, and other applicable keys.
  3. NVDA test: Repeat the predefined tasks.
  4. JAWS test: Repeat exactly the same tasks.
  5. VoiceOver test: Repeat applicable tasks on macOS/Safari.

For every failure, record the module, page/screen, task, assistive technology, browser, WCAG criterion, expected behavior, observed behavior, severity, screenshot, optional short screen recording, and notes.

9. Do Not Count the Same Problem Carelessly

You need a clear unit of analysis. Suppose the same unlabeled “Next” control occurs on 15 screens. Is that 15 accessibility failures, or one recurring defect?

Both measures can be useful, but they answer different questions. I recommend reporting unique defects and defect occurrences separately.

Example: 18 unique accessibility defects representing 73 observed occurrences.

13. Turn “Accessible to All Literacy Levels” into Measurable Requirements

This is likely to be one of the most original parts of the thesis.

Proposed principle: Accessible Cybersecurity Training — Security-awareness content shall be perceivable, operable, understandable, and compatible with commonly used assistive technologies and input modalities.

You could then define measurable subcriteria such as:

  • AT1: All functionality shall be keyboard operable.
  • AT2: Informational images shall have equivalent text alternatives.
  • AT3: Video training shall provide synchronized captions.
  • AT4: Training shall expose meaningful names, roles, and states to assistive technologies.
  • AT5: Quiz feedback and security warnings shall be programmatically announced.
  • AT6: Focus order shall preserve the logical instructional sequence.
  • AT7: Completion shall not require pointer-specific actions.
  • AT8: Accessibility shall be evaluated using defined assistive-technology task tests.

14. Analyze the Results Quantitatively and Qualitatively

Possible quantitative metrics include:

  • Total applicable WCAG criteria
  • WCAG pass rate
  • Failures per training product
  • Failures by WCAG principle
  • Critical/major/moderate/minor failures
  • Task-completion rate
  • Failures by assistive technology
  • Percentage of defects addressed by HCAF
HCAF Coverage = (Accessibility defects addressed by HCAF / Total unique accessibility defects)

The qualitative analysis should explain why those failures matter for cybersecurity. For example, an inaccessible graphic is not merely a website-design defect if the graphic teaches employees the visual indicators of a phishing email.

15. Include an IRB Determination Even Though There Are No Participants

Because the proposed study evaluates publicly available materials and does not recruit people or collect identifiable private information, it may not constitute human-subject research.

However, you should still follow your university's IRB/research-compliance procedure and obtain an official Not Human Subjects Research / IRB determination if your institution uses such a process. Do not simply write “IRB is unnecessary” based on your own determination.

17. Practical Thesis Workflow

Literature review → define research questions → select/freeze training corpus → create task protocol → establish WCAG checklist → configure JAWS/NVDA/VoiceOver environments → automated evaluation → keyboard testing → screen-reader testing → record failures → classify WCAG/severity → calculate task completion/conformance → map failures to HCAF → identify HCAF gaps → develop measurable HCAF accessibility extension → validate proposed criteria against discovered defects → write thesis.

Do not describe this project simply as “running accessibility scanners against HHS and CISA websites.” That would be too shallow for a master's thesis. The stronger contribution is the combination of task-based assistive-technology evaluation + WCAG conformance analysis + cybersecurity-specific impact analysis + formal extension of HCAF.

The technical environment is relatively simple; the rigor needs to come from the experimental protocol, consistent task execution, evidence collection, and the HCAF mapping methodology.

Important Wording Correction for the Proposal

Be careful when describing HIPAA training requirements. HIPAA §164.308(a)(5) requires a security awareness and training program for workforce members. HHS describes periodic security reminders and may recommend activities such as simulated phishing, but the regulation itself should not be described as directly mandating “annual training plus monthly phishing.”
